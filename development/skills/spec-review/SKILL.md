# Spec Review — 기획서 1차 검토 패스

기획서를 받아 **개발자 관점**에서 *놓치기 쉬운 항목*을 4가지 카테고리로 자동 정리한다.

> ⚠️ **이 스킬의 위치**: 1차 패스 보조 도구. 최종 판단은 *사람이 검증*해야 함.
> 부족한 부분은 사용자가 채우거나, 후속 질문으로 보완.

## 트리거

- `spec-review {파일경로}`
- 자연어: "이 기획서 검토해줘", "기획서 1차 정리해줘", "이거 개발자 입장에서 정리해줘"
- 파일 첨부와 함께 자연어 ("이거 검토해줘" + PDF)
- URL 첨부 ("이 페이지 검토해줘" + Confluence·Notion 링크)

## 입력

1. 기획서 — PDF / 이미지 / 텍스트 / Confluence·Notion URL
2. (선택) 추가 컨텍스트
   - "FE 관점만"
   - "BFF API 관점만"
   - "전체 직군 관점"

## 동작 절차

### 1. 기획서 파싱

- **PDF**: Read 도구로 전체 텍스트 추출. 50쪽 이상이면 _섹션 분할_ 권장
- **이미지**: vision 분석
- **URL**: WebFetch로 페이지 본문 가져오기
- **텍스트**: 그대로 사용

### 2. 4가지 카테고리 자동 추출

#### ① 작업 할일 (개발 단위)

*무엇을 만들어야 하는가*를 구현 단위로 분리.

| #   | 작업                     | 예상 소요       | 의존성                 |
| --- | ------------------------ | --------------- | ---------------------- |
| 1   | 화면 / 컴포넌트 / 페이지 | 1~3일 단위 추정 | 백엔드 API / 디자인 등 |

분리 기준:

- 화면 단위
- 신규 API 호출 (훅 단위)
- 상태 관리 (스토어·context)
- 라우팅 / 모달 / 인터랙션
- 외부 라이브러리 도입

#### ② 우려사항 / 기술 리스크

_시작 전에 짚어야 할 위험_. 다음 패턴 자동 감지:

- **비가역 동작**: 마감 / 결제 / 삭제 / 전송 등 — 복구 정책 필요
- **성능 우려**: 대량 데이터 / 무한 스크롤 / 실시간 / 동시 접속
- **보안 우려**: 권한 / 인증 / 개인정보 / 결제정보
- **호환성**: 구버전 브라우저 / 모바일 / 인쇄·PDF / 다크모드
- **데이터 정합성**: timezone / 단위 / null 처리 / enum 값
- **운영 부담**: 모니터링·로그 / 장애 대응 / 롤백

| #   | 항목 | 영향도(高/中/低) | 대응 방안 |
| --- | ---- | ---------------- | --------- |

#### ③ 기술 검토 필요

_결정해야 할 기술 사항_:

- BFF / API 응답 shape 합의
- timezone 표기 (Z vs +09:00)
- snake_case vs camelCase
- 캐시 정책 (react-query staleTime, invalidate 시점)
- 라이브러리 선정 (date picker, chart, 엑셀 다운로드 등)
- 환경별 분기 (.env.dev/.stag/.prod)
- 에러 처리 정책 (403/500 글로벌 vs 로컬)

#### ④ 타 직군 협조 요청

*혼자 해결 못 하는 항목*을 부서별로 정리:

| 부서          | 요청 내용                                               | 우선순위(高/中/低) | 시점 |
| ------------- | ------------------------------------------------------- | ------------------ | ---- |
| 기획자        | 모호한 요구사항 / 정의 필요 항목                        |                    |      |
| 백엔드        | API 명세 / DB 스키마 / 권한 정책 / 데이터 마이그레이션  |                    |      |
| 디자인        | 다크모드 / 모바일 / 에러·빈 상태 화면 / 인터랙션 디테일 |                    |      |
| 인프라/DevOps | 환경변수 / 도메인 / 배포 정책 / CDN / 인증서            |                    |      |
| QA            | 테스트 시나리오 / 엣지 케이스 / 검증 환경               |                    |      |
| 법무·보안     | 개인정보 처리 / 약관 / 보안 점검                        |                    |      |

### 3. 출력 형식

```markdown
# [{기능명}] Spec Review (1차 패스)

출처: {파일명/URL}, p.{페이지 범위}

## ① 작업 할일

| #   | 작업 | 예상 소요 | 의존성 |
| --- | ---- | --------- | ------ |

## ② 우려사항 / 기술 리스크

| #   | 항목 | 영향도 | 대응 |
| --- | ---- | ------ | ---- |

## ③ 기술 검토 필요

- 항목 1
- 항목 2

## ④ 타 직군 협조 요청

| 부서 | 요청 내용 | 우선순위 | 시점 |
| ---- | --------- | -------- | ---- |

---

⚠️ 1차 패스 결과. 사람이 검증 필요.
{기획서에서 *불명확*한 부분이 있다면 마지막에 별도 섹션으로 정리}
```

### 4. 후속 액션 제안 (선택)

분석 후 다음 중 하나 제안:

- "이 결과를 *회의 안건*으로 변환할까?" → 의제·시간 배분 자동
- "_JIRA/Linear 티켓_ 양식으로 변환할까?" → 작업 할일을 티켓별로 분리
- "*기획자에게 보낼 질문 리스트*로 변환할까?" → ②③의 *불명확 항목*만 정리
- "_Confluence 페이지_ 양식으로 변환할까?" → 사내 표준 양식 적용

## 한계 / 주의사항

| 한계                       | 영향                                                      |
| -------------------------- | --------------------------------------------------------- |
| 기획서가 *불완전*함        | 그대로 누락 항목 못 잡음 — 결과에 _불명확 항목_ 별도 표기 |
| _이미지/와이어프레임_ 위주 | 시각 정보 일부 손실 — vision으로 보완하되 100% 아님       |
| _주관적 우려사항_          | Claude는 _일반 패턴_ 기준 — 도메인 특수성은 사용자가 보강 |
| _우선순위·소요·영향도_     | 추정치 — 사용자가 _검증·조정_ 필요                        |
| 50쪽+ 큰 기획서            | 한 번에 처리 어려움 — 섹션 분할 또는 핵심 챕터만 우선     |

## 사용 예시

**입력**: "이 기획서 검토해줘" + 포인트정산\_기획서\_v0.3.pdf

**출력** (요약):

```
# [포인트 정산 메뉴] Spec Review (1차 패스)
출처: 포인트정산_기획서_v0.3.pdf, p.1-12

## ① 작업 할일
| # | 작업 | 예상 소요 | 의존성 |
|---|---|---|---|
| 1 | 월별 현황 페이지 UI | 2~3일 | 디자인 시안 |
| 2 | BFF 4개 엔드포인트 연동 (list/detail/close/excel) | 1~2일 | BE 명세 합의 |
...

## ② 우려사항 / 기술 리스크
| # | 항목 | 영향도 | 대응 |
|---|---|---|---|
| 1 | 마감 처리 비가역 — 실수 시 복구 정책 부재 | 高 | 기획자 문의, 마감 전 confirm |
| 2 | 일간 전환 시 row 수 수천 가능 — 페이징 필요 | 中 | BFF 페이징 파라미터 합의 |
...

## ③ 기술 검토 필요
- BFF 응답 datetime 표기 (Z vs +09:00 — 현재 혼재)
- transactionDetail 항목 수 (11개 vs 21개)
...

## ④ 타 직군 협조 요청
| 부서 | 요청 내용 | 우선순위 | 시점 |
|---|---|---|---|
| 백엔드 | BFF 응답 datetime 표기 통일, 21개 actionDetail 확장 | 高 | 이번 주 |
| 디자인 | 모바일 화면 디자인, 에러 화면 정의 | 中 | 다음 주 |
...

---
⚠️ 1차 패스 결과. 사람이 검증 필요.
```
